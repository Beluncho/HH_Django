сравнение вариантов промтов и параметров поиска, с реальными прогонами и выводом

«Python-разработчик», регион Москва (20 вакансий HH.ru, 57 нормализованных навыков).

## 3. Как запустить и проверить

### 3.1. Без Docker (быстрее всего для проверки)

```bash
git clone https://github.com/Beluncho/HH_Django.git
cd HH_Django
git checkout AI_Agents_diploma

python -m venv venv
venv\Scripts\activate                  # Windows; Linux/macOS: . venv/bin/activate
pip install "Django==5.1.6" "djangorestframework==3.15.2" requests

cp .env.local.example .env.local       # подставить только SECRET_KEY
./run_local.sh migrate
./run_local.sh loaddata demo_analysis
./run_local.sh runserver
```

Адрес `http://127.0.0.1:8000/trainer/`, вход `demo` / `demo1234`. В базе уже лежит
готовый прогон (8 вакансий HH.ru, 36 навыков, объяснения навыков) — ключи HH.ru и LLM
для просмотра не нужны.

### 3.2. Через Docker

```bash
cp .env.dev.example .env.dev           # заполнить HH_ACCESS_TOKEN и LLM_API_KEY
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
```

Адрес `http://localhost:8000/`. Если Docker включён, но `docker compose` не находится —
в этой системе работает `docker-compose` (v1-синтаксис) и `wsl.exe -e docker`.

### 3.3. Повторить эксперименты

```bash
./run_local.sh run_experiment frequency --query "Python-разработчик" --area 1
./run_local.sh run_experiment top-k --query "Python-разработчик" --area 1 --top-k 3,5,8
./run_local.sh run_experiment chunk-size --chunk-size 600,900,1200
./run_local.sh run_experiment embedding --query "Python-разработчик"
./run_local.sh run_experiment prompt-explanation --query "Python-разработчик" --area 1 --prompt-variant 1,2
./run_local.sh run_experiment prompt-evaluation --query "Python-разработчик" --area 1 --prompt-variant 1,2 --answer "..."
```

**Сеть.** Команды обращаются к HH.ru только если анализа для этого запроса и региона ещё
нет. При повторном запуске `run_analysis` возвращает уже выполненный анализ
(`services/analysis.py:139`), поэтому второй прогон воспроизводит те же числа без сети.
Эксперименты 5 и 6 дополнительно требуют рабочего LLM (`LLM_API_KEY`).

**Расхождение в масштабе.** Числа в этом отчёте получены на анализе в 20 вакансий.
Демо-выгрузка `demo_analysis` содержит 8 вакансий и другой запрос (`junior python developer`),
поэтому абсолютные значения там будут меньше — выводы эксперимента от масштаба не зависят.

## 4. Прогонщик экспериментов

Эксперименты выполняет management-команда `run_experiment` — часть самого Django-проекта,
а не отдельный скрипт. Она переиспользует рабочие сервисы приложения
(`run_analysis`, `KnowledgeRetriever`, `explanation_prompt`, `evaluation_prompt`, клиент LLM)
и поэтому проверяет именно тот код, который работает в интерфейсе.

```
python manage.py run_experiment <эксперимент> [параметры]
```

| Эксперимент | Параметры | Нужен LLM |
|---|---|---|
| `frequency` | `--query`, `--area`, `--limit` | нет |
| `top-k` | `--top-k 3,5,8` | нет |
| `chunk-size` | `--chunk-size 600,900,1200`, `--chunk-overlap` | нет |
| `embedding` | `--query` | нет |
| `prompt-explanation` | `--prompt-variant 1,2` | **да** |
| `prompt-evaluation` | `--prompt-variant 1,2`, `--answer`, `--question` | **да** |

Флаг `--out` сохраняет размеченный блок в файл — так получены все шесть файлов в
[`docs/stage4/`](stage4/). Без флага блок печатается только в терминал.

## 5. Почему вместо ноутбука — command-прогонщик

Требование этапа упоминает «финальную версию ноутбука». Ноутбука в проекте нет намеренно,
и это осознанная замена, а не пропущенный пункт.

| Свойство | Ноутбук | Management-команда |
|---|---|---|
| Запуск «с нуля» у проверяющего | нужен Jupyter и порядок ячеек | одна строка, тот же venv, что и у проекта |
| Запуск в Docker / на сервере | нет | да, `docker compose exec web python manage.py ...` |
| Проверка регрессий | нет | входит в `manage.py test candidate_trainer` |
| История изменений | `.ipynb` — JSON, diff нечитаемый | обычный `.py`, видно в `git diff` |
| Источник истины | второй, параллельный код | тот же код, что работает в интерфейсе |

Ноутбук пришлось бы поддерживать как **вторую реализацию** того же пайплайна: любое
изменение в `analysis.py`, `knowledge.py` или `prompts.py` нужно было бы повторять в ячейках,
иначе отчёт перестал бы соответствовать приложению. Команда `run_experiment` вызывает те же
функции, поэтому расхождение между отчётом и приложением невозможно по построению.

Воспроизводимость у команды выше: результат не зависит от порядка выполнения ячеек и
зафиксирован флагом `--out`.

## 6. Эксперименты

### 6.1. Частота навыка: по вакансиям или по упоминаниям

**Цель.** Выбрать способ подсчёта частоты навыка из двух естественных вариантов:
(а) сколько вакансий содержат навык, (б) сколько раз навык упомянут в текстах.

**Гипотеза.** Подсчёт по упоминаниям чувствителен к повторам слова внутри одного описания
и к подстрокам, поэтому ранжирование по нему должно «поехать».

**Команда.**

```bash
./run_local.sh run_experiment frequency --query "Python-разработчик" --area 1
```

**Результат** (фрагмент, полностью — 57 навыков в [сыром блоке](stage4/experiment_frequency.md)):

| Ранг | Навык | Вакансий | Упоминаний |
|---:|---|---:|---:|
| 1 | Python | 12 | 44 |
| 2 | PostgreSQL | 7 | 16 |
| 3 | SQL | 7 | 41 |
| 4 | Git | 5 | 21 |
| 5 | Docker | 4 | 17 |
| 6 | Fastapi | 4 | 11 |
| 7 | API | 3 | 37 |
| 8 | CI/CD | 3 | 18 |
| 9 | Redis | 3 | 9 |
| 10 | REST API | 3 | 7 |

Показательные расхождения внутри той же таблицы:

| Навык | Вакансий | Упоминаний | Что произошло |
|---|---:|---:|---|
| API | 3 | 37 | подстрока «api» внутри *FastAPI*, *OpenAPI* — счёт раздут в 12 раз |
| Ai | 1 | 35 | подстрока «ai» внутри обычных слов — навык попал в таблицу случайно |
| Apache Kafka | 1 | 0 | написание в вакансии отличается от канонического, упоминаний не нашлось |
| Django Framework | 1 | 0 | нормализация развела с «Django» (1 вакансия, 9 упоминаний) |

Итог эксперимента: при подсчёте по упоминаниям позицию меняют **56 навыков из 57**.

**Вывод.** Частота считается **по числу вакансий** (`AnalysisSkill.vacancy_count`), а не по
числу вхождений подстроки. Подсчёт по вакансиям устойчив к повторам внутри одного описания и
к подстрочным совпадениям, а требование «частота = количество исходных вакансий, содержащих
навык» выполняется буквально. Столбец «варианты написания» (`AnalysisSkill.variants`) решает
исходную задачу — учитывать разные написания одного навыка, не прибегая к подстрокам.

### 6.2. Сколько фрагментов RAG отдавать модели (`top-k`)

**Цель.** Подобрать `top-k` — сколько релевантных фрагментов базы знаний попадает в контекст
промта.

**Гипотеза.** Слишком мало — модель отвечает общими словами; слишком много — контекст
разбавляется почти одинаковыми фрагментами и растёт цена запроса.

**Команда.**

```bash
./run_local.sh run_experiment top-k --query "Python-разработчик" --area 1 --top-k 3,5,8
```

**Результат.** Навык — Python, поиск по коллекции `skill-core`:

| Место | Фрагмент | score при k=3 | при k=5 | при k=8 |
|---:|---|---:|---:|---:|
| 1 | Python-разработчик | 0.5929 | 0.5929 | 0.5929 |
| 2 | WEB-разработчик | 0.5854 | 0.5854 | 0.5854 |
| 3 | Python-разработчик (LLM/AI), ритейлер | 0.5342 | 0.5342 | 0.5342 |
| 4 | Senior Python Backend разработчик | — | 0.5328 | 0.5328 |
| 5 | Senior python разработчик (AI-агенты, Data) | — | 0.5244 | 0.5244 |
| 6 | Разработчик python / PgPL разработчик | — | — | 0.4724 |
| 7 | Python-разработчик (Senior/Lead) | — | — | 0.4438 |
| 8 | Python developer | — | — | 0.4399 |

**Вывод.** Выбран **top-k = 5**. Между 5-м и 6-м фрагментом — заметный разрыв
(0.5244 → 0.4724), дальше идут фрагменты того же типа с падающей релевантностью: они
увеличивают промт, не добавляя новых сведений. Первые же три фрагмента почти дублируют друг
друга по смыслу, поэтому k=3 даёт модели слишком узкий срез.

Значение закреплено при объяснении навыка — `KnowledgeRetriever.retrieve(..., limit=5)`
(`services/interview.py:64`). На шаге собеседования контекст ограничен сильнее, там берётся
4 фрагмента (`services/interview.py:115`): вопрос формируется по каждому ответу заново,
и широкий контекст делает диалог менее сфокусированным.

### 6.3. Размер фрагмента базы знаний (`chunk-size`)

**Цель.** Выбрать `max_chars` — на сколько символов режется текст описания вакансии при
наполнении `skill-core`.

**Гипотеза.** Мелкие фрагменты точнее попадают в запрос, но теряют контекст; крупные —
сохраняют контекст, но «размывают» вектор.

**Команда.**

```bash
./run_local.sh run_experiment chunk-size --chunk-size 600,900,1200 --chunk-overlap 120
```

**Результат** (20 описаний вакансий, перекрытие 120 символов):

| `max_chars` | Всего фрагментов | В среднем на вакансию |
|---:|---:|---:|
| 600 | 107 | 5.3 |
| 900 | 68 | 3.4 |
| 1200 | 52 | 2.6 |

**Вывод.** Оставлено значение по умолчанию — **900 символов, перекрытие 120**
(`services/knowledge.py:42`). При 600 фрагмент часто обрывается на середине мысли и
перекрытие 120 символов начинает заметно дублировать текст; при 1200 в один фрагмент
попадают требования из разных смысловых блоков вакансии, и вектор становится менее
конкретным. 900 даёт 3–4 фрагмента на вакансию — достаточно, чтобы сохранить смысл, и
достаточно мелко, чтобы фрагмент был про одну тему.

### 6.4. Модель векторов для поиска (`embedding`)

**Цель.** Сравнить две доступные реализации embeddings: техническую `hash` и реальную
модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`.

**Гипотеза.** `hash` не является семантической моделью и не должен давать осмысленного
ранжирования — он существует для тестов и запуска без `torch`.

**Команда.**

```bash
./run_local.sh run_experiment embedding --query "Python-разработчик"
```

**Результат.** Близость запроса «Python-разработчик» к четырём тестовым фразам:

| Тестовая фраза | `hash` | MiniLM |
|---|---:|---:|
| Опыт разработки на Python и Django, понимание ORM | +0.2500 | **+0.6638** |
| Настройка CI/CD, Docker и Kubernetes | +0.0000 | +0.1761 |
| Вёрстка интерфейсов на JavaScript и React | +0.0000 | +0.1165 |
| Работа с PostgreSQL, оптимизация SQL-запросов | +0.0000 | +0.0483 |

**Вывод.** Используется **sentence-transformers MiniLM** (`EMBEDDING_PROVIDER=sentence_transformers`,
размерность 384). `hash` вырождается: три фразы из четырёх получают ровно нулевую близость,
то есть поиск по таким векторам смысла не различает. Реальная модель даёт градуированную
шкалу, в которой профильная фраза про Python и Django отрывается от остальных в 3,8 раза.
Это согласуется с тем, что уже сохранено в базе: `embedding_model` у коллекции `skill-core`
равен той же модели.

**Важно:** сравнение ничего не переиндексирует. Переход между провайдерами требует
`reindex_embeddings`, иначе в одной коллекции смешаются векторы разных моделей.

### 6.5. Формулировка промта объяснения навыка

**Цель.** Выбрать из двух вариантов промта тот, что даёт лучшее объяснение навыка.

**Гипотеза.** Вариант с явной структурой и указанием границ контекста должен быть полезнее
для подготовки к собеседованию, чем свободный пересказ.

**Команда.**

```bash
./run_local.sh run_experiment prompt-explanation \
  --query "Python-разработчик" --area 1 --prompt-variant 1,2
```

**Результат.** Оба варианта получили одинаковый вход: навык Python и 5 фрагментов
`skill-core`. Ни один из них не придумал внешних источников — оба опираются только на
переданный контекст.

| Критерий | v1 | v2 |
|---|---:|---:|
| Объём ответа, символов | 6 635 | 8 298 |
| Структура | Назначение → Ключевые понятия → Пример → Вопросы → План → **Ограничения** | Зачем нужен → Ключевые понятия → Пример → Вопросы → **План на неделю** |
| Явно названы границы контекста | **да** (раздел «Ограничения») | нет |
| Связь с найденными вакансиями | общая | явная («в контексте вакансий Python требуется для…») |
| Готовый план подготовки | сжатый список | разбит по дням |

Полные тексты обоих вариантов — в [сыром блоке](stage4/experiment_prompt-explanation.md).

**Вывод.** Основным выбран **вариант v1**. Он короче при том же содержании и, главное,
содержит раздел «Ограничения», где модель прямо перечисляет, чего в найденном контексте нет
(анализа данных, машинного обучения, научных вычислений). Это важно по требованию отчёта:
результат работы LLM не должен выглядеть как проверенный внешний источник, и v1 сам
обозначает свои границы. Вариант v2 полезен как альтернативный режим «план подготовки на
неделю» — он конкретнее по дням, но не отделяет найденный контекст от общих знаний модели.

### 6.6. Формулировка рубрики оценки ответа

**Цель.** Выбрать вариант промта, которым модель оценивает ответ кандидата.

**Гипотеза.** Разные формулировки рубрики могут менять не только текст обратной связи, но и
сами оценки.

**Команда.** Вопрос и ответ кандидата заданы фиксированно — чтобы сравнивались именно
промты, а не сгенерированные вопросы:

```bash
./run_local.sh run_experiment prompt-evaluation \
  --query "Python-разработчик" --area 1 --prompt-variant 1,2 \
  --question "Что такое GIL в Python и как он влияет на выбор между многопоточностью и многопроцессностью?" \
  --answer "<ответ на 5 предложений: называет GIL, берёт multiprocessing, не разбирал event loop>"
```

**Результат.** Оценки по рубрике (корректность / глубина / практическое применение):

| Вариант | Корректность | Глубина | Практика |
|---|---:|---:|---:|
| v1 | 3 | 2 | 3 |
| v2 | 3 | 2 | 3 |

Различия — в объяснении, а не в баллах:

| Критерий | v1 | v2 |
|---|---:|---:|
| Пунктов в списке пробелов | 4 | 5 |
| Пробел объяснён («почему это пробел») | кратко | **развёрнуто** |
| Тон обратной связи | персональный: «вы правильно определили…» | общий: «важно не только знать, но и понимать…» |
| Следующий вопрос | про `threading` при GIL | про `threading` при GIL |

Полные ответы обоих вариантов — в [сыром блоке](stage4/experiment_prompt-evaluation.md).

**Вывод.** Основным выбран **вариант v1**: обратная связь адресована кандидату и начинается
с того, что он сделал верно, — это полезнее для обучения. Вариант v2 оставлен как режим
«журнал проверки»: его список пробелов развёрнут и пригоден как обоснование оценки.

Отдельный результат эксперимента: **баллы по рубрике не зависят от формулировки промта**
(3/2/3 в обоих случаях). Это ожидаемо и полезно — значит, числовая оценка устойчива, а
вариант промта влияет только на качество объяснения. Сама оценка при этом остаётся оценкой
LLM и не выдаётся за объективную.

## 8. Ограничения эксперимента

1. Числа получены на одном наборе — 20 вакансий по запросу «Python-разработчик» (Москва).
   Другие запросы и регионы могут дать иные значения `top-k` и размеров фрагментов; команда
   `run_experiment` позволяет повторить серию на любом запросе.
2. Эксперименты 5 и 6 оценивают качество текста, порождённого LLM. Оценка «понятнее и
   полезнее» сделана просмотром ответов, а не формальной метрикой; баллы рубрики — оценка
   самой модели и не считаются объективными.
3. Эксперимент `embedding` — микробенчмарк на четырёх фиксированных фразах. Он показывает
   разницу в качестве векторов, но не заменяет переиндексацию коллекции.
4. При `LLM_MAX_TOKENS` ниже ~3000 ответы модели обрываются на полуслове
   (`finish_reason: length`) — учтено при прогоне, см. `command_run_analysis_demo.md`.
