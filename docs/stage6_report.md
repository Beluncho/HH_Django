# Этап 6. Наблюдаемость и администрирование

Отчёт о доработке тренажёра `candidate_trainer` после ручного тестирования: обратная
связь во время работы, журнал обращений к модели и загрузка базы знаний из браузера.

Доработка сделана 16.10.2026, тремя отдельными коммитами в ветке `AI_Agents_diploma`.
Проверки прогонялись локально, без Docker: `check`, `makemigrations --check`, весь
набор тестов.

---

## 1. Что сделано

| № | Этап | Что решает | Итог |
|---|---|---|---|
| 1 | Индикатор «система работает» | во время запроса не было видно, работает система или повисла | кнопка блокируется и меняет подпись, сверху идёт полоса |
| 2 | Журнал обращений к модели | HTTP 400 от провайдера был недиагностируем | все вызовы пишутся в базу; тексты промтов и ответов — нет |
| 3 | Загрузка базы знаний из админки | методичку можно было положить в RAG только командой | форма в браузере, тот же путь, что у команды |

### 1.1. Все три проблемы — из одного ручного прогона

Доработка началась не с плана, а с проверки тренажёра руками. Три вещи оказались
не косметическими:

1. **Нет обратной связи.** Все действия — обычные HTML-формы без единой строки JS.
   Пока идёт запрос, единственный признак жизни — родная крутилка браузера во вкладке.
2. **Ошибка модели недиагностируема.** Провайдер убрал модель из обслуживания и отвечал
   `{"detail":"Model not supported"}`, а на экране было только «LLM-сервис вернул
   HTTP 400»: тело ответа выбрасывалось, логгера в проекте нет. На разбор ушёл
   отдельный сеанс работы.
3. **База знаний наполняется только командой.** Тяжёлая часть уже была написана, а
   из браузера загрузить методичку было нельзя.

### 1.2. Индикатор «система работает»

Единственный файл с JS в проекте — [trainer.js](../HH/candidate_trainer/static/candidate_trainer/js/trainer.js).
Это прогрессивное улучшение: **без JS приложение работает ровно как раньше**.

Что происходит при отправке формы:

- кнопка блокируется и получает подпись из атрибута `data-busy`;
- на форму ставится `aria-busy="true"`, сверху появляется полоса хода работы;
- возврат по «Назад» из кэша браузера чинится через событие `pageshow`;
- страховая задержка: если через 90 секунд перехода не случилось, кнопка
  возвращается и показывается подсказка — иначе интерфейс остался бы мёртвым.

Обработчик делегирован на `document` и выходит, если `event.defaultPrevented` — поэтому
валидация формы продолжает работать и невалидная форма не залипает. Блокировка кнопки
отложена на `setTimeout(..., 0)`: иначе имя и значение нажатой кнопки не попадут в
отправляемые данные.

Подписи не врут о том, что происходит. Анализ вакансий — это HH API и векторы,
**не** модель, поэтому там «Ищу вакансии и считаю навыки…», а не «модель думает».

| Место | Кнопка | Подпись |
|---|---|---|
| Страница анализа | Анализировать | Ищу вакансии и считаю навыки… |
| Карточка анализа | Повторить анализ | Повторяю анализ… |
| Карточка анализа | Начать собеседование | Готовлю первый вопрос… |
| Карточка анализа | Объяснить | Объясняю… |
| Собеседование | Повторить обработку | Повторяю разбор… |
| Собеседование | Отправить ответ | Разбираю ответ… |

«Завершить собеседование» оставлено без подписи: это быстрая операция без обращения
к модели.

### 1.3. Журнал обращений к модели

Новая модель [`LLMRequestLog`](../HH/candidate_trainer/models.py#L390), миграция
[`0002_llmrequestlog`](../HH/candidate_trainer/migrations/0002_llmrequestlog.py).

Главное поле — `error_detail`: тело ответа провайдера. Ради него всё и делалось.

| Пишем | Принципиально **не** пишем |
|---|---|
| операция (объяснение, первый вопрос, оценка ответа, проверка) | текст промта |
| статус, HTTP-код, тело ответа провайдера | ответ модели |
| провайдер, имя модели | ключ доступа |
| длительность в миллисекундах | |
| расход токенов, если провайдер его вернул | |
| пользователь, если запрос пришёл из интерфейса | |

Поля для текста промта и ответа отсутствуют в модели, а не просто не заполняются —
этого требует `AGENTS.md`. Тест проверяет это, обходя все поля модели.

Запись идёт через контекстный менеджер
[`record_llm_call`](../HH/candidate_trainer/services/llm_log.py#L47): он замеряет время
и пишет строку и на успехе, и на ошибке, а исключение пропускает дальше. Так
[`llm.py`](../HH/candidate_trainer/services/llm.py) остаётся инфраструктурным и не
импортирует модели. **Журнал не может сломать основную операцию:** если запись в базу
не удалась, ошибка глушится, а исходное исключение всё равно поднимается.

Обёрнуты все четыре операции: объяснение навыка, первый вопрос, оценка ответа и
команда `check_llm`. Оценка ответа обёрнута вместе с разбором структуры ответа, поэтому
некорректный ответ модели тоже попадает в журнал как ошибка.

Второй элемент — [`humanize_llm_error`](../HH/candidate_trainer/services/llm.py#L45):
перевод ответа провайдера в короткую подсказку.

| Что ответил провайдер | Что видит пользователь |
|---|---|
| `Model not supported` | провайдер не обслуживает модель — проверьте `LLM_MODEL` |
| `Unsupported parameter: 'max_tokens'` | подсказка про `LLM_MAX_TOKENS_PARAM` |
| `Unsupported value: 'temperature'` | подсказка очистить `LLM_TEMPERATURE` |
| 401 / 403 | проверьте `LLM_API_KEY` |
| 429 | провайдер ограничил частоту запросов |
| остальное | общая фраза и указатель на журнал |

В админке журнал — только для чтения, с фильтрами по статусу, операции и провайдеру и
поиском по телу ошибки ([LLMRequestLogAdmin](../HH/candidate_trainer/admin.py#L190)).

### 1.4. Загрузка базы знаний из админки

Сначала закрыт доступ на запись к производным данным — иначе админка стала бы способом
**молча** сломать поиск:

- фрагменты ([KnowledgeChunkAdmin](../HH/candidate_trainer/admin.py#L154)) — только
  чтение: правка текста без пересчёта вектора разводит фрагмент и его embedding, и
  поиск начинает находить не то, что написано;
- у коллекции ([KnowledgeCollectionAdmin](../HH/candidate_trainer/admin.py#L53)) только
  чтение для `slug`, `embedding_model` и `embedding_dimension` — их правка обошла бы
  защиту от смешивания векторов разных моделей. Зато выключатель `enabled` вынесен в
  список: выключить retrieval — рутинная операция;
- документ ([KnowledgeDocumentAdmin](../HH/candidate_trainer/admin.py#L136)) нельзя
  создать руками: такой документ остаётся без фрагментов и молча не находится.

Потом — сама загрузка: отдельная страница в админке с формой
([KnowledgeImportForm](../HH/candidate_trainer/forms.py#L55)), файл `.txt`, `.md` или
`.json`, название, тип источника, URL и необязательная привязка к навыку.

**Команда и админка идут одним путём.** Подготовка содержимого вынесена в
[`prepare_document_content`](../HH/candidate_trainer/services/knowledge.py#L89), а
оркестрация — в новый модуль
[knowledge_import.py](../HH/candidate_trainer/services/knowledge_import.py). Команда
`import_knowledge` теперь вызывает то же самое и стала тоньше. Два входа в одну базу
знаний иначе разошлись бы в деталях вроде привязки к навыку.

Несовпадение embedding-модели коллекции показывается как ошибка формы, а не как 500:
после смены модели это обычная ситуация, а не сбой.

## 2. Как проверить

### 2.1. Автоматические проверки

```bash
./run_local.sh check
./run_local.sh makemigrations --check --dry-run
./run_local.sh test
```

Результат прогона 16.10.2026:

| Проверка | Результат |
|---|---|
| `check` | `System check identified no issues (0 silenced).` |
| `makemigrations --check --dry-run` | `No changes detected` |
| `test` (весь проект) | `Ran 112 tests ... OK` |
| `test candidate_trainer` | `Ran 90 tests ... OK` |

Два новых модуля — `test_llm_log` и `test_knowledge_import` — это 24 теста из этих 90.
Тесты, как и раньше, не обращаются ни к HH.ru, ни к провайдеру модели, ни к Hugging
Face: embedding подменяется тестовым провайдером `hash`, ответы модели — фейками.

**Замечание про консоль Windows.** В старом приложении `hhapp` команда
[`full_db.py`](../HH/hhapp/management/commands/full_db.py#L20) печатает эмодзи, и на
консоли в кодировке cp1251 набор тестов падает с `UnicodeEncodeError` — это свойство
кодировки, а не тестов. Обход на один запуск:

```bash
PYTHONIOENCODING=utf-8 ./run_local.sh test
```

### 2.2. Журнал: сбой провайдера воспроизведён вживую

Чтобы проверить перевод ошибки, а не только тесты, был воспроизведён реальный сбой:
во временном файле настроек подменено только имя модели на несуществующее, и запущена
проверка `check_llm`.

Пользователь увидел:

```text
CommandError: LLM-сервис вернул HTTP 400. Ответ провайдера: {"detail":"Model not supported"}
```

В журнале появилась строка:

```text
check | error | http: 400 | provider: OpenAI | model: google/model-that-does-not-exist | duration_ms: 4797
```

Штатный вызов записался как успешный:

```text
ok | check | http: None | tokens: 18 1
```

Строка содержит и код, и тело ответа провайдера, и время — то есть разбор занял бы
минуты вместо отдельного сеанса.

### 2.3. Ручные проверки

1. **Индикатор.** Пройти шесть кнопок из таблицы в разделе 1.2 в браузере. Отдельно:
   отправить форму с заведомо коротким запросом — должна появиться ошибка валидации, а
   кнопка не должна остаться заблокированной.
2. **Загрузка знаний.** В админке: «Коллекции знаний» → «Загрузить документ», положить
   `.md` в коллекцию `interview`. Убедиться, что появились фрагменты и что собеседование
   их подхватывает (порядок — в
   [инструкции по настройке](candidate_trainer_setup.md), раздел 7).

## 3. Ограничения и следующий шаг

1. **Индексация синхронная.** Загрузка документа выполняется прямо в запросе
   браузера. Первый вызов скачивает embedding-модель (около 470 МБ), дальше каждый
   фрагмент считается на CPU — для большой методички это минуты, и всё это время
   страница ждёт. Фоновая индексация — это уже отдельный этап с Celery.
2. **Оригинал файла не сохраняется.** В базе остаются фрагменты и имя файла в
   метаданных. Это осознанное решение, а не недоделка: смысл хранится во фрагментах,
   а хранение исходников — отдельный вопрос с правами доступа.
3. **Журнал не чистится.** Записи копятся без ограничения срока хранения. Для дипломного
   объёма это неважно, но перед реальной эксплуатацией нужна ретенция.
4. **Порога релевантности при поиске по базе знаний по-прежнему нет.** Известное
   ограничение этапа 4, здесь не менялось.
5. **Ошибки по-прежнему разбираются вручную.** Понятная фраза и журнал дают материал
   для разбора, но автоматической реакции на сбой (повтор, уведомление) нет.
